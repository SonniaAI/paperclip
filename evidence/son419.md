# SON-419 — /instructions, /tasks, /activity, settings, CSV import

## What shipped

All four §12/§11/§4.5/§4.6 feature areas are now wired as authenticated API
routes on top of the `20260809_son419` migration (which was staged with the
models/schemas/service layer in earlier slices but never connected to the
app).

| Area | Routes | Behaviour |
| --- | --- | --- |
| `/instructions` | GET `/api/instructions`, POST, PATCH `/{slug}`, GET `/{slug}/history` | Editable with **version history**. Each edit supersedes the active version (immutable history) and publishes the next version with an `effective_from` ("in effect since") timestamp. Exactly one active version per topic via a partial unique index. |
| `/tasks` | GET/POST `/api/tasks`, PATCH `/api/tasks/{id}`, GET/POST `/api/task-lists` | My Tasks (private default, owner set) vs Team Tasks (shared)/Lists. Visibility toggle always present; private rows are only visible to their owner at the query layer. Markdown bodies accepted. |
| `/activity` | GET `/api/activity` | One chronological feed (`activity_log_feed_idx`), filter by action type + actor, cursor-based infinite scroll, `private` entries hidden from everyone except the actor. |
| Settings | profile, security (change password, TOTP enrollment already existed, session list + revoke, security-event log), company, team, billing (non-functional top-up, contact-us), integrations | Password changes + session revokes record `security_events` with IP/UA. |
| CSV import | POST `/api/contacts/import/preview`, POST `/api/contacts/import` | Column mapping inference, preview (created/merged/skipped estimates), dedupe by normalised email + E.164 phone (within-file and against the DB), durable `contact_imports` summary run. |
| Onboarding | GET/PATCH `/api/onboarding` | §4.6 state machine `pending → instructions → import → invite → complete` on `organizations.onboarding_state`. |

## Notes / remaining concerns

- `e2e_auth_flow.mjs` now applies the `son419` migration too, because the
  `Organization` ORM model already referenced `onboarding_state`; the auth e2e
  must run on the full schema chain.
- Billing "top-up" is intentionally non-functional (`action: contact_us`) per
  the §4.5 Phase 1 scope; integrations list existing rows only (no provider
  enrolment UI yet).
- The activity/feed and settings pages are backend-complete; the frontend that
  calls these routes is a separate Phase 1 workstream.
